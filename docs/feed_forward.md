# SwiGLU 前馈网络性能实验

## 1. 实验目标

本实验实现一个基于 PyTorch 的 SwiGLU 前馈网络，并在 NVIDIA GeForce RTX 4060 Laptop GPU 上测试不同序列长度和数据类型对推理性能的影响。

实验重点包括：

1. 理解 SwiGLU 前馈网络的计算结构。
2. 分析 FP32、FP16 和 BF16 的参数显存差异。
3. 比较不同数据类型下的推理延迟和吞吐量。
4. 观察短序列与长序列对 GPU 利用率的影响。
5. 为后续 Transformer Decoder Block 和大模型推理优化实验建立基础。

## 2. 网络结构

实验中的前馈网络使用如下 SwiGLU 结构：

```text
FFN(x) = Down(SiLU(Gate(x)) ⊙ Up(x))
```

其中：

- `Gate`：将隐藏维度从 `H` 投影到中间维度 `I`。
- `Up`：将隐藏维度从 `H` 投影到中间维度 `I`。
- `SiLU`：非线性激活函数。
- `⊙`：逐元素乘法。
- `Down`：将中间维度从 `I` 投影回隐藏维度 `H`。

数据形状变化如下：

```text
输入：
(B, S, H)

Gate 和 Up 投影后：
(B, S, I)

逐元素相乘后：
(B, S, I)

Down 投影后：
(B, S, H)
```

其中：

- `B`：Batch Size。
- `S`：Sequence Length。
- `H`：Hidden Size。
- `I`：Intermediate Size。

## 4. 参数量与理论参数显存

SwiGLU 前馈网络包含三个权重矩阵：

```text
gate_proj：H × I
up_proj：  H × I
down_proj：I × H
```

因此，不包含 Bias 时的参数总量为：

```text
参数量 = H × I + H × I + I × H
       = 3 × H × I
```

代入实验配置：

```text
参数量 = 3 × 1024 × 4096
       = 12,582,912
```

不同数据类型的理论参数显存为：

| 数据类型 | 单个参数字节数 | 参数显存 |
|:---:|---:|---:|
| FP32 | 4 Bytes | 48 MiB |
| FP16 | 2 Bytes | 24 MiB |
| BF16 | 2 Bytes | 24 MiB |

FP16 和 BF16 的参数显存均为 FP32 的一半。

这里统计的只是模型参数本身的理论存储空间，不包含输入、输出、中间激活、PyTorch CUDA 缓存和其他运行时开销，因此不等同于整个程序的峰值显存。

## 5. 实验方法

每种 Sequence Length 和数据类型组合均进行三轮独立测试。

每轮测试过程如下：

1. 创建 SwiGLU 前馈网络。
2. 将模型和输入转换为指定数据类型。
3. 执行预热迭代，减少首次执行时初始化开销的影响。
4. 使用 CUDA Event 测量 GPU 执行时间。
5. 根据平均延迟计算模块的 token 吞吐量。
6. 记录模型参数量、理论参数显存和输出形状。

实验结果以三次独立运行的：

```text
均值 ± 样本标准差
```

表示。

吞吐提升倍数通过各数据类型的平均吞吐量相对于 FP32 平均吞吐量计算。

## 7. 结果分析

### 7.1 低精度显著降低参数显存

FP32 参数占用48 MiB，而 FP16 和 BF16 均为24 MiB，减少了50%。

这是因为：

```text
FP32：每个参数占4字节
FP16/BF16：每个参数占2字节
```

对于本实验中的前馈网络，数据类型改变不会影响参数数量，只会改变每个参数的存储大小。

对于大语言模型而言，FFN 通常包含大量参数，因此降低权重精度可以明显减少模型权重占用和权重读取的数据量。

### 7.2 长序列具有更高的 token 吞吐量

以 FP32 为例，Sequence Length 从1增加到512后：

```text
4,537 tokens/s → 263,276 tokens/s
```

虽然总延迟从约0.2204 ms 增加到约1.9451 ms，但一次前向计算处理的 token 数量增加了512倍，因此单位时间内处理的 token 数量显著提高。

这说明：

> 延迟增加和吞吐量提高可以同时发生。

当 Sequence Length 较小时，GPU 需要执行的计算量有限，固定的 Kernel Launch、调度和访存开销占比较高，GPU 的大量计算资源可能没有得到充分利用。

当 Sequence Length 增大时，Linear 层对应的矩阵乘法规模变大，GPU 可以并行处理更多数据，因此整体吞吐量提高。

### 7.3 FP16 和 BF16 均显著优于 FP32

不同 Sequence Length 下，低精度相对于 FP32 的吞吐提升如下：

| Sequence Length | FP16 提升 | BF16 提升 |
|---:|---:|---:|
| 1 | 2.25× | 1.90× |
| 16 | 4.43× | 4.58× |
| 128 | 3.14× | 3.39× |
| 512 | 3.63× | 3.62× |

在所有测试配置中，FP16 和 BF16 的平均吞吐量均高于 FP32。

可能原因包括：

1. FP16 和 BF16 每个元素只占2字节，减少了数据读取量。
2. 较低精度可以提高有效显存带宽利用率。
3. GPU 可以使用适合低精度矩阵计算的硬件执行路径。
4. 长序列对应更大的矩阵乘法，更容易发挥 GPU 的并行计算能力。

不过，本实验没有使用硬件性能分析工具验证具体 Kernel 和硬件执行单元，因此这里只能将这些原因作为与实验结果一致的解释，不能据此断言某个具体硬件单元一定被使用。

### 7.4 Decode-like 工作负载的 GPU 利用率较低

Sequence Length 为1时，输入形状为：

```text
(1, 1, 1024)
```

它可以近似表示大模型 Decode 阶段中“一次处理一个新 token”的 FFN 计算形状。

此时三个 Linear 层面对的矩阵规模较小，FP32 吞吐量只有约4,537 tokens/s。即使使用 FP16 和 BF16，吞吐提升也低于部分长序列配置。

这说明短序列、低 Batch 的计算不容易充分利用 GPU。

但需要注意，本实验只测试了一个独立 FFN，不包含：

- Self-Attention
- KV Cache
- Token Sampling
- 多层 Decoder
- CPU 调度
- Kernel Launch 之外的推理框架开销

因此，它只能称为 `decode-like` 工作负载，不能直接等同于完整 LLM 的 Decode 性能。

### 7.5 Prefill-like 工作负载具有更高并行度

Sequence Length 为128或512时，FFN 可以一次处理大量 token，更接近 LLM Prefill 阶段的计算形状。

在 Sequence Length 为512时：

```text
FP32：约263,276 tokens/s
FP16：约954,895 tokens/s
BF16：约953,580 tokens/s
```

FP16 和 BF16 都获得了约3.6倍的吞吐提升，说明较大的矩阵乘法能更充分地体现低精度计算优势。

同样，本实验没有包含 Attention，因此这里只能说明 FFN 部分的 Prefill-like 行为。

### 7.6 FP16 和 BF16 没有稳定的绝对胜负

在部分配置中 BF16 更快，例如：

- Sequence Length 16
- Sequence Length 128

而在 Sequence Length 1时，FP16 平均吞吐量高于 BF16。

在 Sequence Length 512时，两者的平均吞吐量非常接近：

```text
FP16：954,894.6 tokens/s
BF16：953,579.8 tokens/s
```

两者差距仅约0.14%，不足以支持“FP16 一定更快”或“BF16 一定更快”的结论。

因此，更严谨的结论是：

> 在当前硬件和实验配置下，FP16 与 BF16 的整体性能处于相近水平，具体差异会随矩阵形状和运行状态变化。

### 7.7 部分 FP16 结果存在较明显波动

FP16 在以下配置中的标准差较大：

- Sequence Length 1
- Sequence Length 16
- Sequence Length 512

例如，Sequence Length 为512时：

```text
平均吞吐量：954,894.6 tokens/s
标准差：126,074.7 tokens/s
```

检查原始结果可以发现，第一轮 FP16 延迟为约0.6313 ms，而第二、三轮分别约为0.5081 ms和0.4895 ms。

这种波动可能与以下因素有关：

- 笔记本 GPU 动态频率
- 功耗模式
- 温度变化
- 后台程序
- 固定实验顺序造成的热机效应
- 测试次数较少
- 不同矩阵形状选择了不同的底层实现

相比之下，BF16 在 Sequence Length 512时较为稳定：

```text
延迟：0.5370 ± 0.0052 ms
吞吐量：953,579.8 ± 9,370.8 tokens/s
```

不过，三轮实验数量仍然较少，不能因此得出 BF16 必然比 FP16 稳定的普遍结论。

## 8. 主要结论

本实验可以得到以下结论：

1. 实现的 SwiGLU FFN 能保持输入输出形状一致，即从 `(B,S,H)` 映射回 `(B,S,H)`。
2. 当前配置下 FFN 共有12,582,912个参数。
3. FP16 和 BF16 将理论参数显存从48 MiB降低到24 MiB，减少50%。
4. FP16 和 BF16 在所有测试序列长度下均比 FP32 具有更高吞吐量。
5. Sequence Length 墑大后，总延迟增加，但 token 吞吐量也显著提高。
6. Sequence Length 为1的 Decode-like 计算难以充分利用 GPU。
7. 长序列的 Prefill-like 计算具有更大的矩阵规模和更高并行度。
8. FP16 与 BF16 性能整体接近，不能根据三轮实验断言其中一种始终更快。
9. 笔记本 GPU 的性能测试存在运行间波动，报告均值的同时应保留标准差。
10. 当前 `tokens/s` 是单个 FFN 模块处理隐藏状态的吞吐量，不是完整大模型每秒生成的 token 数。

## 9. 实验局限

本实验仍存在以下局限：

1. 只在一张 RTX 4060 Laptop GPU 上测试。
2. 只测试一个 FFN 模块，并非完整 Transformer。
3. 没有测试不同 Batch Size。
4. 没有记录 GPU 温度、频率和功耗。
5. 只进行了三轮独立实验。
6. 不同数据类型始终按固定顺序运行，可能引入顺序偏差。
7. 只统计参数理论显存，没有测量实际峰值显存。
8. 没有使用 PyTorch Profiler、Nsight Systems 或 Nsight Compute 分析底层 Kernel。
9. 没有比较 FP16、BF16 和 FP32 的数值误差。
10. 没有测试不同 Hidden Size 和 Intermediate Size。
