# 最小 Decoder-only Transformer 前向性能实验

## 1. 实验目标

本实验在已经实现的 RMSNorm、RoPE、Causal Multi-Head Self-Attention、SwiGLU FFN 和 Transformer Decoder Block 基础上，组装一个能够完成前向计算的最小 Decoder-only Transformer 语言模型。

实验目标包括：

1. 验证 Token Embedding、多层 Decoder Block、最终 RMSNorm 和 LM Head 的完整数据流。
2. 验证模型输出形状、参数量、权重共享和端到端因果性。
3. 分析序列长度及 FP32、FP16、BF16 对完整模型前向延迟和输入 token 吞吐量的影响。
4. 比较三种精度下的理论参数显存和执行期间额外峰值显存。
5. 为后续实现自回归生成、KV Cache 以及 Prefill/Decode 分阶段测试建立无缓存基线。

当前模型使用随机初始化权重，实验只验证模型结构、数值性质和执行性能，不具备有意义的自然语言生成能力。

## 2. 模型结构

完整前向数据流为：

```text
input_ids: (B, S)
       │
       ▼
Token Embedding
       │
       ▼
Transformer Decoder Block × 4
       │
       ▼
Final RMSNorm
       │
       ▼
LM Head
       │
       ▼
logits: (B, S, V)
```

每个 Decoder Block 内部采用 Pre-Norm 结构，并包含 RoPE Causal Self-Attention、SwiGLU FFN 和两条残差连接。模型默认共享 Token Embedding 与 LM Head 的权重：

```text
lm_head.weight = token_embedding.weight
```

权重共享避免重复保存一个形状为 `(vocab_size, hidden_size)` 的权重矩阵。

## 4. 参数量与理论参数显存

共享词嵌入权重时，模型参数由以下部分构成：

```text
Token Embedding：V × H
单个 Decoder Block：4H² + 3HI + 2H
4 个 Decoder Block：L × (4H² + 3HI + 2H)
Final RMSNorm：H
LM Head：与 Token Embedding 共享，不重复计数
```

代入本实验配置：

```text
参数量 = V × H + L × (4H² + 3HI + 2H) + H
       = 8192 × 512
         + 4 × (4 × 512² + 3 × 512 × 2048 + 2 × 512)
         + 512
       = 20,976,128
```

三轮实验得到的参数量均与理论值一致。

| 数据类型 | 单参数字节数 | 理论参数显存（MiB） | 相对 FP32 |
|:---:|---:|---:|---:|
| FP32 | 4 | 80.0176 | 100% |
| FP16 | 2 | 40.0088 | 50% |
| BF16 | 2 | 40.0088 | 50% |

FP16 和 BF16 均将模型参数的理论存储空间降低约 50%。这里仅统计参数，不包括输入、隐藏状态、Attention Score、Logits、CUDA Context 和 PyTorch 缓存分配器保留的显存。

## 5. 正确性验证

单元测试覆盖以下性质：

1. 输入 `(B, S)` 的 Token ID 能够得到 `(B, S, V)` 的 Logits。
2. `ModuleList` 中 Decoder Block 数量与配置一致。
3. 开启权重共享时 LM Head 与 Token Embedding 指向同一权重，关闭时二者相互独立。
4. 模型参数量与理论公式一致。
5. 修改未来位置的 Token ID 不影响过去位置的 Logits，验证完整模型保持因果性。
6. 模型输出均为有限值，不包含 NaN 或 Inf。
7. 显式传入 `position_ids` 时能够正确完成前向计算。
8. 非法模型配置、输入维度、Token ID 类型和超长序列能够触发预期异常。

## 6. 实验方法

对每种 Sequence Length 和数据类型执行以下步骤：

1. 使用固定随机种子创建模型和输入 Token ID。
2. 将模型参数转换为待测数据类型并移动至 GPU。
3. 执行 5 次预热，使相关 CUDA Kernel 和运行时状态完成初始化。
4. 使用 CUDA Event 测量 20 次完整模型前向计算的总时间并计算单次平均延迟。
5. 使用 `sequence_length / latency` 计算 Batch Size 为 1 时的输入 token 吞吐量。
6. 根据唯一参数的元素数量和数据类型统计理论参数显存。
7. 使用 PyTorch CUDA Memory API 记录计时阶段相对基线的额外峰值已分配显存。
8. 独立运行三轮，报告均值与样本标准差。

本实验的 `input_tokens_per_second` 表示一次完整前向中处理已有输入 token 的速率。它既不是自回归生成速度，也不能直接当作真实服务中的输出 tokens/s。

## 8. 结果分析

### 8.1 模型前向链路与参数注册正确

所有输出形状均为 `(1, S, 8192)`，说明 Token Embedding、4 个 Decoder Block、Final RMSNorm 和 LM Head 已经连接为完整的前向链路。实测参数量为 20,976,128，与开启权重共享后的理论结果完全一致。

端到端因果性测试不仅覆盖单个 Attention 或 Decoder Block，还跨越了词嵌入、多层堆叠和输出投影。该测试保证修改未来 Token ID 时，过去位置的 Logits 不发生变化。

### 8.2 低精度稳定降低参数显存

FP32 参数需要约 80.02 MiB，FP16/BF16 只需要约 40.01 MiB，均降低约 50%。该收益与序列长度无关，因为模型权重数量不会随输入长度改变。

额外峰值显存也大体体现低精度优势：在 `S=1、16、128` 时，FP16/BF16 的额外峰值正好约为 FP32 的一半；在 `S=512` 时，FP32 为 39.25 MiB，而 FP16/BF16 为 30.75 MiB，低精度降低约 21.7%。

`S=512` 时额外峰值没有下降一半，可能与当前实现中的 FP32 Softmax、Attention Score、RoPE 和 RMSNorm 临时张量，以及多个张量生命周期重叠有关。这里记录的是相对计时前基线的 PyTorch 峰值已分配显存，并不等价于完整进程显存，也不能单独定位某个算子的实际显存占用。

### 8.3 长序列下低精度计算优势明显

`S=512` 时三种精度的平均结果为：

```text
FP32： 82,635.2 tokens/s
FP16：155,582.2 tokens/s，约为 FP32 的 1.88 倍
BF16：135,382.1 tokens/s，约为 FP32 的 1.64 倍
```

序列较长时，各层线性投影和 Attention 矩阵乘法规模增大，Tensor Core 与较低内存流量带来的收益更容易覆盖 Kernel Launch、类型转换和逐元素运算等固定开销。因此，低精度在本实验最大 Shape 上表现出清晰优势。

### 8.4 短序列下低精度不保证更低延迟

`S=1` 时，FP16 和 BF16 的平均吞吐只有 FP32 的 0.79 倍和 0.82 倍；`S=16` 时三者接近；`S=128` 时 FP16/BF16 仍未稳定超过 FP32。

完整模型由 4 个 Decoder Block 组成，每层包含多个小 Kernel。短序列时单个矩阵乘法规模较小，Kernel Launch、因果 Mask 构造、RoPE 三角函数、归约、FP32 中间计算和类型转换等开销所占比例较高。消费级 GPU 的动态频率和后台负载也更容易影响毫秒级测量。因此不能从参数减半直接推导出短序列延迟减半。

### 8.5 BF16 在部分 Shape 下波动较大

`S=128` 的 BF16 延迟为 `4.3178 ± 1.4127 ms`，`S=512` 为 `3.9325 ± 1.0102 ms`。其中 `S=128` 的三轮 BF16 原始延迟分别约为 5.50、2.76 和 4.69 ms，波动明显；而 `S=512` 的第三轮也出现约 5.10 ms 的较慢结果。

这些原始结果被保留并计入统计，没有人为删除。可能的影响因素包括笔记本 GPU 动态功耗与温度、不同运行轮次的频率状态、后台 GPU 活动以及较少的预热和正式迭代次数。当前数据足以观察总体趋势，但不足以声称 FP16 与 BF16 在所有 Shape 上存在稳定的性能排序。

后续可以通过以下方式提高测量稳定性：

- 固定 GPU 性能状态或至少记录温度、频率和功耗；
- 增加预热与正式迭代次数；
- 对测试顺序进行随机化或交错执行；
- 报告中位数、P10/P90 等分位数；
- 使用 `torch.profiler` 或 Nsight Systems 定位异常轮次。

### 8.6 序列增长提高设备利用率，但不能视为生成加速

FP32 输入吞吐从 `S=1` 的约 401 tokens/s 增长到 `S=512` 的约 82,635 tokens/s，并不是模型“生成得更快”，而是一次并行前向处理了更多已知 Token，GPU 利用率随计算规模提高。

当前 `S=1` 仅表示没有历史上下文的一次单 Token 前向。真实自回归 Decode 需要让当前 Token 关注之前的 K/V；若尚未实现 KV Cache，则每一步都要重新计算不断增长的完整前缀。因此，本实验结果更接近 Prefill 形态的无缓存基线，不能直接代表 TTFT、TPOT 或端到端生成吞吐。

## 9. 实验结论

1. 成功将已有核心组件组装为 4 层最小 Decoder-only Transformer，并通过 Shape、参数量、权重共享和端到端因果性测试。
2. 模型共有 20,976,128 个唯一参数；FP16/BF16 将理论参数显存从 80.02 MiB 降低到 40.01 MiB。
3. `S=512` 时 FP16/BF16 的输入吞吐约为 FP32 的 1.88 倍和 1.64 倍，长序列下低精度优势明显。
4. `S≤128` 时低精度性能优势不稳定，说明固定开销、实现细节和运行环境会显著影响小 Shape 性能。
5. BF16 在部分配置中存在较大运行间波动，后续结论应结合更长测试、分位数和 Profiler 数据。
6. 当前实验只测量随机权重模型的完整前向，不代表模型质量或真实自回归生成速度。

## 10. 后续工作

下一阶段将基于该模型继续实现：

1. Greedy 自回归生成，建立无 KV Cache 的逐 token 生成基线。
2. 将推理过程拆分为 Prefill 和 Decode，并分别测量延迟。
3. 在 Attention 层加入逐层 KV Cache，并验证缓存前后 Logits 一致性。
4. 对比无缓存与有缓存生成的复杂度、TPOT、吞吐量和显存增长。
5. 在稳定的完整模型基线上继续实现 INT8 weight-only 量化。
